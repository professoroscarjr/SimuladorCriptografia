Bem-vindo ao Cofre

Imagine que seu banco de dados é um grande cofre de banco. Se alguém roubar o cofre, interceptar o carro-forte ou se o próprio gerente for mal-intencionado, como protegemos o que está lá dentro?

Texto Claro

Dados originais, legíveis por qualquer pessoa.

Nome: João da Silva
Cartão: 4111 1111 1111 1111

Texto Cifrado

Dados embaralhados por um algoritmo e uma chave.

0x01000000D0C8B...9A8F7
V2FqZTIzOTFqM...

Por que isso importa?

Leis como a LGPD exigem que dados sensíveis (CPFs, cartões, saúde) sejam protegidos. Na nossa aula, veremos que **não existe uma criptografia única**, mas sim "camadas de proteção" dependendo de onde o dado está.

Criptografia em Trânsito

Protege os dados enquanto eles viajam pelo "carro-forte" da rede.

Servidor SQL

A Analogia

É como enviar uma carta dentro de um envelope blindado. O carteiro (a internet) carrega o envelope, mas não consegue ler o que está escrito no papel lá dentro.

Ataque Evitado

Man-in-the-Middle (Homem no meio). Evita que um hacker num Wi-Fi público intercepte a rede e roube a senha viajando do celular até o servidor.

Criptografia em Repouso (TDE)

TDE - Transparent Data Encryption. Protege os arquivos físicos do banco parados no disco.

Transparente para a Aplicação

O banco de dados (SQL Server, por exemplo) criptografa os dados antes de salvá-los no disco rígido (arquivos .mdf, .ndf) e descriptografa quando carrega na memória.

A aplicação nem sabe que isso acontece (por isso é "transparente"). Não é necessário alterar nenhuma query (SELECT, INSERT).

A Analogia

O prédio do banco e as paredes do cofre são indestrutíveis de fora para dentro. Ninguém entra para roubar à força.

Ataque Evitado

Roubo físico do HD no Data Center ou cópia não autorizada do arquivo de Backup (o hacker leva o backup pra casa, mas não consegue anexar sem o certificado).

Nível de Coluna

Proteção cirúrgica. Em vez de criptografar o banco todo, miramos em dados específicos.

Criptografia Granular

ID Nome Completo NumCartaoCredito
1 Maria Oliveira 0x01000000D0C8B9A8F...
2 Carlos Souza 0x01000000E1D9C0B9E...

Vantagem

Altamente seguro contra leitura não autorizada. Se um funcionário tem acesso de leitura (SELECT) na tabela, ele verá os nomes, mas o cartão aparecerá como "lixo" se ele não tiver a chave de descriptografia ou permissão.

Desvantagem

Afeta a performance. O banco usa CPU para criptografar/descriptografar via funções internas (`ENCRYPTBYKEY`). Fazer buscas (WHERE) nessas colunas se torna lento, e índices tradicionais não funcionam bem.

Always Encrypted

O "Padrão Ouro". O Servidor SQL nunca vê o dado em texto claro.

Chaves Mestre aqui!

Aplicação (Driver)

Criptografa ANTES de enviar.

0x8F9A...

Servidor SQL

Só armazena. Não tem a chave.

O pesadelo do DBA mal-intencionado

Geralmente, o Administrador de Banco de Dados (DBA) tem poder total. No TDE ou Criptografia de Coluna, um DBA com acesso root consegue, teoricamente, chegar aos dados.

Com o Always Encrypted, a criptografia acontece na aplicação (no cliente, ex: código C# ou Java). O banco só recebe dados cifrados. Se o DBA executar um SELECT * FROM Tabela, ele só verá "lixo". Ele precisaria invadir o servidor da aplicação para pegar a chave.

Hashing vs Criptografia

Um parêntese muito importante sobre senhas.

Criptografia

É uma via de mão dupla. Você embaralha e, com a chave, pode desembaralhar.

"secreta" "0x1A2B" "secreta"

Hashing

É uma via de mão única (Liquidificador). Você transforma, mas é matematicamente impossível reverter para o original.

"123mudar" "a665a45920422f9d417e4867efdc4fb8a04a1f3fff1fa07e998e86f7f7a27ae3"

Regra de Ouro da Segurança

Senhas NUNCA devem ser criptografadas no banco. Elas devem sofrer Hashing (com um Salt).

O banco salva o Hash. Quando você faz login, o sistema gera o Hash da senha que você digitou e compara com o Hash salvo no banco. Se os hashes baterem, você entra. Assim, se o banco vazar, ninguém sabe qual era sua senha real.
